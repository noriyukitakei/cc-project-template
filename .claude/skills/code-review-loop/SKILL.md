# コードレビュー 並列ループの進め方

コード変更を**4観点で並列レビュー → 集約 → 致命的・高がゼロになるまで修正・再レビュー**する工程の正本。
本スキルは「**誰をいつ起動し、結果をどう集約して次にどうするか**」だけを定義する。各観点の判断基準・報告フォーマット・的外れ指摘の回避などの共通規律は [[code-review-conventions]] が持ち、各観点のチェックリストは各エージェントが持つ。

## 前提：観点分担（重ねない）
- **reviewer-security** … セキュリティ（脆弱性・秘密情報・認証認可）
- **reviewer-correctness** … 正確性・品質（バグ・データ破壊・エラー処理・テスト不足・デッドコード）
- **reviewer-performance** … パフォーマンス（非効率・N+1・ブロッキングI/O・キャッシュ）
- **reviewer-maintainability** … 保守性・可読性（構造の複雑さ・命名・重複・ベストプラクティス）

各エージェントは**自分の観点だけ**を見る（他観点に踏み込まない）。これにより指摘が重複せず、並列実行できる。

## 起動の流れ
1. **対象を確定** … レビュー対象（変更したファイル群。`git diff --staged` / `git diff` で把握）と、参照すべき設計ドキュメントを決める。
2. **並列レビュー** … 4観点を**同時に**起動する。1つのメッセージ内で複数の `Agent` 呼び出しを並べて並列実行する：
   - `Agent(subagent_type: "reviewer-security")`
   - `Agent(subagent_type: "reviewer-correctness")`
   - `Agent(subagent_type: "reviewer-performance")`
   - `Agent(subagent_type: "reviewer-maintainability")`

   各 prompt に「レビュー対象ファイル群」「参照すべき設計ドキュメント」を渡す。
3. **集約** … 4観点の報告を1つにまとめる。観点ごとのサマリ表（致命的/高/中/低の件数）を統合し、**全観点を通じた最終判定**を出す：
   - いずれかに**致命的**があれば **却下(BLOCK)**
   - 致命的ゼロだが**高**があれば **要注意(WARNING)**
   - 致命的・高がゼロなら **承認(APPROVE)**
   - 同一箇所に複数観点が触れている場合は重複を1件にまとめて提示する。
4. **修正ループ** … 下記ルールで回す。

## ループ制御（CLAUDE.md フェーズ4の条件に準拠）
- **継続条件**: 致命的・高の指摘が1件以上 → コードを修正し、影響した観点（または全観点）を再度並列起動して再レビュー。
- **正常終了**: 致命的・高がゼロになった時点でループを抜ける。
- **異常終了**: 3回修正してもなお致命的・高が残る場合はループを停止し、残存する指摘内容をユーザーに提示して人間の判断を求める。

## 各ターンで人間に返すもの
- 統合サマリ（観点別の件数表＋全体判定 APPROVE/WARNING/BLOCK）
- 今が何周目か
- 致命的・高の指摘の一覧（ファイル:行・壊れるシナリオ・修正方法）
- 異常終了時は、残存指摘と人間に判断してほしい点を明示

## 効率の注意
- 4観点は独立なので必ず**並列**で起動する（直列にしない）。
- 変更が極小で観点が明らかに無関係な場合（例: ドキュメントのみの変更）は、関係する観点だけに絞ってよい。絞った場合は「どの観点を省いたか」を報告に明記する。
