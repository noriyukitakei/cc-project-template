# 要件定義書作成スキル

このスキルは要件定義書を作成するためのスキルです。

## 前提条件

要件定義書を作成する前に以下のタスクが完了している必要があります。

### アイデアの検討が完了している

プロダクトのアイデアは、あらかじめ対話で整理・具体化しておく必要があります。

### docs/ideas/idea-summary.md が作成されている

**重要**: 対話を通じて整理した内容は、次のファイルに保存しておく必要があります。

**ファイルパス**: `docs/ideas/idea-summary.md`

## 要件定義書の標準構成

以下の構成を基本とする。

1. プロダクト概要
2. プロダクトコンセプト
3. ターゲットユーザー
4. 機能要件
5. 非機能要件

## 要件定義書の詳細

### プロダクト概要

プロダクトの目的や背景、解決したい課題を簡潔にまとめる。

この項目では、少なくとも次の内容を書く。

- なぜこのプロダクトが必要なのか
- 現在どのような課題があるのか
- その課題を解決することで何を実現したいのか

### プロダクトコンセプト

プロダクトが提供する価値を一言で表し、どのような体験を目指すのかを整理する。

この項目では、少なくとも次の内容を書く。

- どのような価値を提供するプロダクトか
- 既存のやり方や競合と比べて何が違うのか
- ユーザーにどのような印象や体験を提供したいのか

### ターゲットユーザー

主な利用者を明確にし、それぞれがどのような状況で使うのかを整理する。

この項目では、少なくとも次の内容を書く。

- 想定しているユーザー層は誰か
- ユーザーはどのような課題や目的を持っているか
- どのような利用シーンでプロダクトを使うのか

### 機能要件

プロダクトに必要な機能を一覧化し、ユーザーが何をできるようになるかを整理する。

この項目では、少なくとも次の内容を書く。

- 必須機能とあると望ましい機能
- 各機能でユーザーが実行できる操作
- 機能ごとの入力、出力、保存されるデータ

### 非機能要件

機能以外で満たすべき条件を整理し、運用や品質の観点を明確にする。

この項目では、少なくとも次の内容を書く。

- 可用性に関する要件
- 性能に関する要件
- セキュリティに関する要件

可用性では、少なくとも次の内容を書く。

- 利用可能な時間帯や停止可能な時間帯
- 障害時にどの程度まで業務継続を求めるか
- バックアップ、復旧、冗長化の考え方

性能では、少なくとも次の内容を書く。

- 想定する利用者数やアクセス量
- 画面表示、検索、登録処理などの応答時間の目安
- 性能劣化を防ぐために必要な条件や制約

セキュリティでは、少なくとも次の内容を書く。

- 認証、認可、権限管理の方針
- 通信や保存データの保護に関する要件
- ログ管理、監査、脆弱性対策に関する要件

## 要件定義書作成プロセス

### 1. idea-summary.md の確認

まず、ユーザーが作成したアイデア検討のメモを確認します。これには、プロダクトの目的や背景、ターゲットユーザー、機能のアイデアなどが含まれているはずです。

```bash
Read('docs/ideas/idea-summary.md')
```

### 2. 要件定義書ドラフトの生成

idea-summary.mdの内容をもとに、テンプレート(`./template.md`)に従って要件定義書を生成します。作成した要件定義書は、`docs/specs/requirements-definition.md`に保存します。


### 3. 要件定義書のレビューと改善

生成された要件定義書を以下の観点でレビューします。

- 背景、課題、実現したいことがつながっており、なぜ作るのかが説明できるか
- ターゲットユーザーと利用シーンが具体的で、誰がいつ使うのかが曖昧でないか
- 機能要件が利用者、入力、出力、保存データまで整理されているか
- 非機能要件が可用性、性能、セキュリティの3観点で不足なく書かれているか
- 要件が実装や後続設計で判断できる粒度になっており、抽象的な表現だけで終わっていないか
- スコープ内とスコープ外、必須と任意が区別できるか
- 関係者が読んで誤解しやすい表現や、確認が必要な前提条件が残っていないか

レビューで不足や曖昧さが見つかった場合は、以下の順で改善します。

1. 曖昧な表現を、判断可能な表現に書き換える
2. 抜けている項目を idea-summary.md の内容から補完する
3. idea-summary.md にない前提や制約は、未確定事項として明示する
4. 実装、設計、テストに引き継ぐ上で不足する観点があれば追記する

特に、次のような記述はそのまま残さない。

- 「使いやすくする」「高速にする」など、基準が不明な表現
- 利用者や操作主体が不明な機能説明
- 入出力や保存データが不明な機能要件
- 障害時運用や権限管理の考え方が抜けた非機能要件

レビュー完了時には、少なくとも次の状態になっていること。

- 要件定義書だけを読んで、対象プロダクトの目的、利用者、主要機能、非機能要件を説明できる
- 後続の基本設計で責務分割を始められる程度に、要件の境界が整理されている
- 未確定事項、確認待ち事項、前提条件が区別されている

必要に応じて、レビュー結果として以下も合わせて残す。

- 要件定義書で確定した事項
- 保留した事項と確認先
- 次の設計フェーズで重点的に詰める論点

### 4. ユーザー承認の取得

要件定義書が完了したら、次の工程に進む前に、必ず承認を得てください。このフェーズでユーザーとの質疑応答を繰り返し、ユーザーが納得行くまで要件定義書を改善してください。

### 5. 要件定義書の保存

ユーザーの承認を得て完成となった要件定義書は、`docs/specs/requirements-definition.md`に保存してください。
