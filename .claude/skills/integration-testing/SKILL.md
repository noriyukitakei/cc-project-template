# 結合テスト仕様書作成スキル

このスキルは結合テスト仕様書を作成するためのスキルです。

## 前提条件

結合テスト仕様書を作成する前に以下のタスクが完了している必要があります。

- **詳細設計書が完成している**
	結合テストでは、画面、API、DB、バッチ、外部IFなどの接続点を検証します。接続仕様、入出力、エラー時の挙動が詳細設計で確定していない場合は、先に詳細設計書を作成してください。承認済みの詳細設計書は `docs/specs/detailed-design.md` に保存されているはずです。
- **結合対象の一覧と境界が明確になっている**
	どのコンポーネント同士を接続して何を確認するのかが曖昧なままだと、観点漏れや重複が発生します。画面、フロントエンド、バックエンド、データベース、外部サービス、バッチ処理の責務境界を整理してから着手してください。

## 結合テスト仕様書の標準構成

以下の構成を基本とする。

1. テスト方針
2. テスト対象範囲
3. テスト環境方針
4. テストデータ方針
5. テストケース一覧

## テストケースの記述形式

各テストケースは、見出し直下に固定フィールドのメタブロックを置き、その後に詳細セクションを続けるブロック形式で記述する（`./template.md` 参照）。

```markdown
## IT-AUTH-002 Redis障害時ログイン確認

- **ID**: IT-AUTH-002
- **観点**: 外部サービス障害
- **実行手段**: manual
- **理由**: Redis停止という外部状態の再現が自動環境で不安定なため

### 概要
...
### 前提条件
...
### 入力
...
### 手順
...
### 期待結果
...
```

メタフィールドの規約は以下のとおり。

- **ID**: 見出しとフィールドの両方に持たせる。テストコード名・CIレポート・実行管理を貫通する共通キーとして使う（例: テスト名に `IT-AUTH-002` を含める）。
- **観点**: 「テスト観点」で定義した観点名を記載する。
- **実行手段**: そのケースを実行する手段を1語で固定する（自由文禁止）。`pytest`（API↔DB↔外部連携をコードで）や `playwright`（画面をまたぐ連携をブラウザで）などプロジェクトの技術スタックで定義したツール名、または自動化しない場合は `manual`。**結合テストは同一レベル内で実行手段が混在しうる**ため、ケースごとにこの値で実行手段を明示する（旧 `自動化` 項目を `manual` 値で兼ねる）。後段はこの値で実行手段ごとにグループ化して `test-loop` を起動する。
- **理由**: `実行手段: manual` の場合は必須とし、なぜ自動化できないかを1行で書く。ツールを指定した場合は `-` でよい。理由を残すことで、後から手動ケースを棚卸しし、技術の進歩に応じて自動化を再評価できる。
- 合否などの実行結果はここに書かない。仕様書は仕様の正本であり、結果は CI / 実行管理側で持つ。

結合テストは、段取り・障害注入・状態遷移が入力から導出できないため、自動化する全ケースで **手順** を必須とする（手順がテストコード生成の入力になる）。手順は「段取りと観測ポイント」の粒度で書き、セレクタやエンドポイントURL、assert する具体値などの実装詳細はテストコード側に委ねる。

## 結合テストの基本原則

以下の原則を踏まえてテスト仕様書を作成する。

**コンポーネント間の責務境界を検証する**

単体テストで確認済みの内部ロジックを繰り返し検証するのではなく、インターフェース、データ受け渡し、トランザクション境界、エラー伝播など、結合点で発生しうる不整合に重点を置く。

**本番に近い接続条件を意識する**

結合テストでは、単体テストよりも実運用に近い設定値、通信方式、シリアライズ形式、DB制約を反映する。外部サービスを本物に接続しない場合でも、少なくとも本番仕様に整合するモックサーバーやテストコンテナを用いる。

**再実行可能で環境を汚染しない**

何度実行しても同じ結果が得られるように、テストデータの投入、初期化、ロールバック、後始末を定義する。共有環境を使う場合は、データ衝突とテスト順依存を避ける。

**障害時の振る舞いを正常系と同等に重視する**

結合テストでは、正常系だけではなく、通信失敗、タイムアウト、整合性違反、外部サービスエラー時に、利用者向けレスポンス、ログ、再試行、回復処理が仕様どおりかを確認する。

**観測可能性を担保する**

失敗時に原因追跡できるよう、ログ、メトリクス、トレース、監査記録のどこで確認するかをテストケースに含める。期待結果には画面表示やレスポンスだけでなく、永続化結果やログ出力も含める。

## テスト観点

**テストケースを作成するとき、必ず以下の観点を確認し、該当するものをすべてカバーすること。** テンプレートの観点欄にはここで定義した観点名を記載する。

### インターフェース連携

| 観点 | 内容 |
| --- | --- |
| 画面-API連携 | 画面入力がAPIリクエストに正しく変換され、レスポンスが画面表示に正しく反映されるか |
| API-DB連携 | APIで受け取ったデータが正しいテーブル・カラムに永続化され、取得時に正しく復元されるか |
| API-外部サービス連携 | 外部API、メッセージキュー、メール送信などの呼び出し条件、送信内容、応答処理が正しいか |
| バッチ-DB連携 | バッチ処理が想定どおりにデータを読み書きし、対象レコードを過不足なく処理するか |
| データ形式整合性 | JSON、日時、数値、列挙値、文字コードなどがシステム間で欠損・変換ミスなく受け渡されるか |
| バージョン互換性 | API仕様差分やスキーマ差分がある場合に、互換性を維持した連携ができるか |

### 業務フロー

| 観点 | 内容 |
| --- | --- |
| 正常系シナリオ | 利用者の主要操作が開始から完了まで期待どおりに完走するか |
| 状態遷移 | 画面、DB、業務ステータスが正しい順序で遷移するか |
| 複数機能連携 | 登録後の一覧反映、更新後の再取得、削除後の参照不可など、機能横断の整合性が取れているか |
| 排他制御 | 同一データへの同時更新時に競合が適切に検知・制御されるか |
| 冪等性 | 同一要求の再送やリトライが重複登録・重複実行を引き起こさないか |

### トランザクション・データ整合性

| 観点 | 内容 |
| --- | --- |
| コミット/ロールバック | 処理成功時のみコミットされ、途中失敗時は不整合なくロールバックされるか |
| 複数テーブル整合性 | 親子テーブル、履歴テーブル、集計データなどの整合性が保たれるか |
| 参照整合性 | 削除・更新時に外部キーや論理整合が破綻しないか |
| 再処理整合性 | 処理途中失敗後に再実行した際、重複や欠損なく復旧できるか |
| タイムゾーン・時刻整合性 | 画面表示、API値、DB保存値で日時の解釈がずれないか |

### 異常系・障害対応

| 観点 | 内容 |
| --- | --- |
| バリデーションエラー伝播 | 入力エラーが適切なHTTPステータス、メッセージ、画面表示として返るか |
| 外部サービス障害 | タイムアウト、5xx、接続失敗時に、再試行、代替処理、利用者通知が仕様どおりか |
| DB障害 | 制約違反、接続断、ロック競合発生時に適切にエラー処理されるか |
| 部分失敗 | 一部処理のみ成功した場合に、整合性が壊れず回復可能な状態を保てるか |
| ログ・監査 | 障害時に必要なログ、監査記録、相関IDが出力され、原因追跡できるか |

### 非機能・運用

| 観点 | 内容 |
| --- | --- |
| 権限・認可連携 | 画面、API、データアクセスの各層で権限制御が一貫しているか |
| セキュリティヘッダ・CORS | ブラウザ経由の連携で必要なヘッダ、CORS設定、CSRF対策が正しく動作するか |
| 設定値差異 | 環境変数、接続先URL、機能フラグの違いで挙動が破綻しないか |
| 監視・アラート前提 | 障害時に監視対象となるログ、メトリクス、アラート条件が確認できるか |
| 性能劣化の兆候 | 想定件数での主要シナリオ実行時に、明らかなタイムアウトや極端な劣化がないか |

## テストデータと環境の方針

- 結合テストに個人情報や本番データを使用しない
- テストデータはシナリオごとに初期状態、実行手順、期待される更新後状態を定義する
- DB初期化方法、外部サービスのスタブ設定、非同期ジョブの起動条件を文書化する
- 共有環境を使う場合は、データの命名規則、テナント分離、掃除手順を明示する
- 時刻依存、ジョブ実行依存、非同期イベント依存のケースは、待機条件や完了判定を明記する

## 結合テスト仕様書作成プロセス

### 1. 関連ドキュメントの確認

まず、承認済みの要件定義書、基本設計書、詳細設計書を確認し、どのコンポーネント間を接続して何を検証するかを整理する。

```bash
Read('docs/specs/requirements-definition.md')
Read('docs/specs/basic-design.md')
Read('docs/specs/detailed-design.md')
```

### 2. 結合対象とテスト範囲の整理

以下を一覧化する。

- 対象機能と対象シナリオ
- 接続対象となるコンポーネントの組み合わせ
- 実接続するものとスタブ化するもの
- 正常系、異常系、回復系の優先度

単体テストで担保する範囲と重複しないように、結合点の確認事項へ寄せて整理する。

### 3. 結合テスト仕様書ドラフトの生成

テンプレート（`./template.md` がある場合はそれに従う）に沿って、結合テスト仕様書を生成する。

**保存先**: `docs/tests/integration/<フロー名>.md`（例: `docs/tests/integration/user-auth-flow.md`）

- フロー名はテスト対象のユーザーフロー・シナリオを表すケバブケースとする
- **ファイルが既に存在する場合**: ファイルの末尾に新しい機能のセクションを追記する。既存の内容は変更しない
- **ファイルが存在しない場合**: 新規作成する

機能追加でテストを追記する際のセクション形式:

```markdown
## <機能名>（YYYY-MM-DD 追加）

### テストケース一覧
...
```

### 4. 結合テスト仕様書のレビューと改善

生成された結合テスト仕様書を以下の観点でレビューする。

- 要件定義書の主要業務フローが、少なくとも1つ以上の結合シナリオで検証対象になっているか
- 基本設計書、詳細設計書で定義された接続点がテスト対象として漏れていないか
- 正常系だけでなく、外部IF障害、DB障害、バリデーションエラー、再実行などの異常系が含まれているか
- 期待結果に、画面表示、レスポンス、DB状態、ログ出力のいずれを確認するかが明記されているか
- テストデータの初期化方法と後始末が定義され、再実行可能になっているか
- 実施環境の前提条件、スタブ利用方針、非同期処理の待機条件が明確か

レビューで不足や曖昧さが見つかった場合は、以下の順で改善する。

1. 対象シナリオと接続点の漏れを補完する
2. 期待結果を観測可能な表現に書き換える
3. テストデータ、環境前提、後始末を追記する
4. 単体テストと重複するケースを削減し、結合観点に寄せる

特に、次のような記述はそのまま残さない。

- 「連携できることを確認する」だけで、何を見て判定するか不明な記述
- 外部サービスや非同期処理の前提が未記載のテストケース
- 正常系のみで、失敗時のロールバックや通知を確認しない計画
- 画面確認だけでDB更新やログ出力の確認観点がないケース

レビュー完了時には、少なくとも次の状態になっていること。

- 結合テスト仕様書だけを読んで、どの接続点をどの環境でどう検証するか説明できる
- 正常系、異常系、回復系の主要シナリオが識別できる
- 実装者またはQA担当者が、そのままテスト実施または自動化に着手できる粒度になっている

必要に応じて、レビュー結果として以下も合わせて残す。

- 単体テストで担保済みとして結合テスト対象外にした範囲
- 実機接続が難しくスタブで代替する範囲と理由
- 総合テストまたは受け入れテストへ持ち越す論点

### 5. ユーザー承認の取得

結合テスト仕様書が完了したら、次の工程に進む前に、必ず承認を得てください。

### 6. 結合テスト仕様書の保存

ユーザーの承認を得て完成となった結合テスト仕様書を保存してください。

- 既存ファイルへの追記の場合: 該当ファイルの末尾にセクションを追記する
- 新規ファイルの場合: `docs/tests/integration/<フロー名>.md` として保存する
