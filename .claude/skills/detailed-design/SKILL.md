# 詳細設計書作成スキル

このスキルは詳細設計書を作成するためのスキルです。

## 前提条件

詳細設計書を作成する前に以下のタスクが完了している必要があります。

- **基本設計書が完成している**  
  詳細設計書は基本設計で定義した内容に基づき、システムの内部仕様を定義するものです。基本設計が完了していない場合は、先に基本設計書を作成してください。承認済みの基本設計書は `docs/specs/basic-design.md` に、API仕様は `docs/specs/api/openapi.yaml` に保存されているはずです。

## 詳細設計書の標準構成

以下の構成を基本とする。プロジェクトの特性上不要なセクションがある場合は、ユーザーに確認のうえ省略してよい。

1. 処理シーケンス
2. クラス設計
3. コーディング規約
4. ストレージ物理設計
5. 各種一覧
6. 外部インターフェース設計

## 詳細設計書の詳細

### 処理シーケンス

プログラムの処理フローとオブジェクト間の相互作用を定義する。機能の特性に応じて以下の図を使い分ける。兼用・組み合わせも可。

- **シーケンス図**（`sequenceDiagram`）: 複数のオブジェクト間のメッセージのやりとりを時系列で示す。API呼び出し・DB操作など、システム間の通信が中心になる機能に向いている
- **アクティビティ図**（`flowchart`）: 条件分岐・ループが多い処理の制御フローを示す。バッチ処理や複雑な業務フローに向いている

どちらの図も mermaid 記法で作成し詳細設計書に埋め込む。mermaid で表現しきれない場合は draw.io 等を使用してよい。

### クラス設計

システムを構成するクラスとその関係を定義する。

- **クラス図**（`classDiagram`）: クラス・属性・メソッド・クラス間の関係を示す。mermaid 記法で作成し詳細設計書に埋め込む。クラス数が多い場合はレイヤーや機能単位で分割してもよい
- クラス一覧: 全クラスの責務・配置パッケージ・依存関係を一覧化する
- 共通オブジェクト・共通機能として切り出せるものを抽出し、重複実装を防ぐ

mermaid で表現しきれない場合は draw.io 等を使用してよい。

### 実装方針

命名規則・インデント・フォーマットはlintやフォーマッタ（PEP8 / ESLint / Prettier等）に委ねる。設計書には**ツールで強制できない判断基準**だけを定義する。

少なくとも次の内容を書く。

- プロジェクト構成（ディレクトリ構成・レイヤー分割の方針）
- エラー処理の方針（例外の種類・ユーザーへの通知方法）
- ログ設計方針（下記参照）
- 禁止事項（lintでは検出しにくい設計レベルの制約）

#### ログ設計方針

ログはトレーサビリティとアラート判断の基盤となるため、以下を必ず定義する。

**リクエストトレーシング**

リクエスト単位でログを追跡できるよう、受信時に一意のリクエストID（UUIDなど）を採番し、そのリクエストで出力するすべてのログに付与する。これにより、エラー発生時に「どのリクエストのどの処理で何が起きたか」を一連の流れとして追跡できる。

**ログレベルの定義**

単に重要度の名前として使うのではなく、「このレベルのログが出たら誰がいつ何をすべきか」まで定義する。

- `DEBUG`: 開発・調査時のみ使う詳細情報。本番では原則出力しない
- `INFO`: 正常系の処理完了記録。ビジネス上重要なイベント（ログイン成功・注文確定など）を残す。アラートは不要
- `WARN`: 今すぐ対処が必要なクリティカルな障害ではないが、放置・頻発するとシステムに影響が出る事象。例: リトライ発生・外部API遅延・非推奨APIの呼び出し。翌営業日までに原因を確認する運用を推奨
- `ERROR`: 即時対応が必要な障害。例: DB接続失敗・予期しない例外・データ不整合。アラート通知と合わせて使い、発生から XX 分以内に担当者が確認する運用とする
- `CRITICAL` / `FATAL`: システム全体が停止・継続不能な致命的障害。例: アプリ起動失敗・設定ファイル読み込み不能。即時エスカレーションが必要

**ログに含める項目**

最低限以下を含める。

- タイムスタンプ（ISO 8601形式）
- ログレベル
- リクエストID（トレーシング用）
- メッセージ
- エラー発生時: スタックトレース・エラーコード

### ストレージ物理設計

基本設計のスキーマ定義を実装レベルに具体化する。基本設計書（`docs/specs/basic-design.md`）のスキーマ定義に追記する形でもよい。

少なくとも次の内容を定義する。

- 物理テーブル名・カラム名（命名規則に従った実際の名前）
- インデックス設計（検索・結合・ソートで使用するカラムへのインデックス付与）
- 制約の詳細（CHECK 制約・デフォルト値・参照整合性）
- パーティショニング・アーカイブ方針（大量データが想定される場合）

### 各種一覧

実装に必要な共通定義を一覧化する。必要なものだけ作成する。

- パラメータ一覧: 設定ファイルや環境変数で管理するパラメータの一覧
- コード一覧: ステータス・区分・種別など、システム内で使用するコード値の一覧
- メッセージ一覧: ユーザーに表示するエラーメッセージ・確認メッセージの一覧

### 外部インターフェース設計

他システムとの連携がある場合に、その仕様を定義する。

少なくとも次の内容を書く。

- 接続先・操作方法
- プロトコル・データ形式
- 認証・セキュリティ
- エラー・例外処理の方針

## 詳細設計書作成プロセス

### 1. 基本設計書の確認

承認済みの基本設計書を確認し、詳細設計に必要な情報を把握する。

```bash
Read('docs/specs/basic-design.md')
Read('docs/specs/api/openapi.yaml')
```

### 2. 詳細設計書ドラフトの生成

基本設計書の内容をもとに、テンプレート（`./template.md`）に従って詳細設計書を生成し、`docs/specs/detailed-design.md` に保存する。

プロジェクトの技術スタック（基本設計書のアーキテクチャ設計「技術スタック」セクションに記載）を踏まえ、コーディング規約・クラス設計・ストレージ物理設計をプロジェクトに合わせて具体化すること。

### 3. 詳細設計書のレビューと改善

生成された詳細設計書を以下の観点でレビューする。

- 基本設計の全機能・全APIに対してシーケンス図が作成されているか
- クラス図が基本設計のアーキテクチャ設計と整合しているか
- 実装方針がプロジェクトの技術スタックに対応しているか
- インデックス設計が API や画面の検索条件を考慮しているか
- コード一覧・メッセージ一覧が機能要件で使用するすべての値を網羅しているか
- 外部連携がある場合、インターフェース設計が基本設計の機能構成と整合しているか

レビューで不足や矛盾が見つかった場合は、以下の順で改善する。

1. 基本設計との矛盾を修正する
2. 抜けているクラス・シーケンス・コード値を補完する
3. 技術スタックに合わない実装方針を修正する
4. 実装者がそのまま実装に入れる粒度に調整する

特に、次のような記述はそのまま残さない。

- 基本設計に記載されたAPIや画面に対応するシーケンス図がない状態
- インデックスが一切定義されていないテーブル（PK のみの状態）
- 「適切に処理する」「必要に応じて対応する」など判断基準が不明な記述

レビュー完了時には、少なくとも次の状態になっていること。

- 詳細設計書だけを読んで、実装者が各機能のクラス・メソッド・処理フローを把握できる
- 実装方針（プロジェクト構成・エラー処理・ログ設計・禁止事項）が具体的に定義されており、実装者間でブレが生じない
- ストレージ物理設計が実装に使用できる粒度で定義されている

### 4. ユーザー承認の取得

詳細設計書が完了したら、次の工程に進む前に、必ず承認を得てください。

### 5. 詳細設計書の保存

ユーザーの承認を得て完成となった詳細設計書は、`docs/specs/detailed-design.md` に保存してください。
