# 機能追加スキル

このスキルは、詳細設計以降の実装フェーズを担うスキルです。ユーザーから機能要求を聞き、設計ドキュメントを参照してタスクリストを作成・確認した後、実装・コードレビュー・ドキュメント更新・テストまでを一貫して進めます。

## 全体の流れ

```
フェーズ1: 機能要求のヒアリング
    ↓
フェーズ2: タスクリストの作成・確認
    ↓ ユーザー承認
フェーズ3: 実装（タスクを順番に実行し、完了したらチェック）
    ↓
フェーズ4: コードレビューと修正ループ（code-review-loop / 4観点並列）
    ↓ 致命的・高の指摘がゼロ
フェーズ5: ドキュメントの更新
    ↓
フェーズ6: テスト仕様作成・実施（V字モデル）
```

---

## フェーズ1: 機能要求のヒアリング

### 1-1. 設計ドキュメントの読み込み

まず以下のドキュメントをすべて読み込んでください。実装はこれらに基づいて行います。

```
Read('docs/specs/requirements-definition.md')
Read('docs/specs/basic-design.md')
Read('docs/specs/detailed-design.md')
```

ファイルが存在しない場合は、その旨をユーザーに伝え、利用可能なドキュメントのみで進めてよいか確認してください。

### 1-2. 機能要求のヒアリング

ユーザーに「どんな機能を追加したいですか？」と聞き、以下の観点で情報を引き出してください。一度にすべて聞かず、会話の流れに合わせて深掘りしてください。

- **機能の目的**: なぜこの機能が必要か
- **機能の概要**: 何ができるようになるか
- **対象ユーザー・画面**: 誰が使う機能か、どの画面・APIか
- **受け入れ条件**: どうなれば完成と見なすか
- **制約・注意点**: 既存機能への影響、パフォーマンス要件など

### 1-3. 設計との整合性確認

ヒアリング内容と読み込んだ設計ドキュメントを照合し、以下を確認してください。

- 要求が要件定義の範囲内か（範囲外であればユーザーに確認）
- 既存の基本設計・詳細設計と矛盾がないか
- 新たに設計変更が必要な箇所がある場合はユーザーに報告する

---

## フェーズ2: タスクリストの作成・確認

### 2-1. タスクリストの作成

ヒアリング内容と設計ドキュメントをもとに、実装に必要なタスクを洗い出します。

**タスク設計の指針:**
- タスクは「1つのファイルまたは1つの責務の単位」で分割する
- 依存関係を明示する（例:「T3はT1完了後」）
- 独立して実施できるタスクは「並行実行可能」と明記する

**タスクに含めるべき種類（該当するもの）:**
- データモデル・マイグレーション
- バックエンド実装（API、ビジネスロジック、バリデーション）
- フロントエンド実装（コンポーネント、APIクライアント）
- 設定・環境変数の追加
- 既存コードへの変更・修正

### 2-2. タスクリストのファイル保存

以下のパスにタスクリストを保存してください。

- **保存先**: `changes/YYYYMMDD-<機能名スラッグ>/tasklist.md`
  - 日付は実行日（例: `20260514`）
  - 機能名スラッグは英語のケバブケース（例: `user-authentication`）
  - 例: `changes/20260514-user-authentication/tasklist.md`

**tasklist.md のフォーマット:**

```markdown
# タスクリスト: <機能名>

作成日: YYYY-MM-DD  
ステータス: 進行中

## 機能概要
<ヒアリングした機能要求の要約>

## 受け入れ条件
- <条件1>
- <条件2>

## タスク

### グループ1: <カテゴリ名>（並行実行可能）
- [ ] T1: <タスク内容>
- [ ] T2: <タスク内容>

### グループ2: <カテゴリ名>（T1, T2 完了後）
- [ ] T3: <タスク内容>

### グループ3: <カテゴリ名>（T3 完了後）
- [ ] T4: <タスク内容>
- [ ] T5: <タスク内容>

## 参照ドキュメント
- 要件定義: `docs/specs/requirements-definition.md`
- 基本設計: `docs/specs/basic-design.md`
- 詳細設計: `docs/specs/detailed-design.md`
```

### 2-3. ユーザー確認・承認

タスクリストの内容をユーザーに提示し、以下を確認してください。

- タスクの抜け漏れがないか
- タスクの粒度・順序が適切か
- 優先度や順番に変更があるか

**承認を得てからフェーズ3へ進んでください。** 承認なしに実装を開始しないでください。

---

## フェーズ3: 実装

### 3-1. 実装の進め方

タスクリストのグループ順に、タスクを1つずつ実装します。

**各タスクの実装手順:**

1. tasklist.md を読み込み、未完了（`- [ ]`）のタスクを確認する
2. 次に実施するタスクを選ぶ
3. **必ず** `docs/specs/requirements-definition.md`・`docs/specs/basic-design.md`・`docs/specs/detailed-design.md` を参照しながら実装する
4. タスクが完了したら、即座に tasklist.md の該当行を `- [x]` に更新する
5. 次のタスクへ進む

**実装中に判断に迷ったとき:**
- 設計ドキュメントに記載がある場合はそれに従う
- 記載がない場合はユーザーに確認する（実装を止めて確認を優先する）

### 3-2. タスク完了チェックの更新

タスクが完了するたびに tasklist.md を更新します。

```markdown
# 更新例
- [x] T1: Userテーブルのマイグレーション作成  ← 完了したらxを付ける
- [ ] T2: ログインAPIの実装  ← まだなら空のまま
```

すべてのグループが完了したら、tasklist.md の先頭の `ステータス: 進行中` を `ステータス: 完了` に更新してください。

### 3-3. 実装完了の確認

すべてのタスクが完了したら、フェーズ4（コードレビュー）へ進みます。

---

## フェーズ4: コードレビューと修正ループ

実装したコードの品質を確保するため、`Skill('code-review-loop')` を呼び出し、**4観点（security / correctness / performance / maintainability）を並列でレビュー**して、致命的・高の指摘がなくなるまで修正します。

### 4-1. レビューの実施

`code-review-loop` に従い、4観点のレビューエージェントを**1メッセージ内で同時に起動**して並列レビューします。各 prompt にレビュー対象（変更したファイル群）と参照すべき設計ドキュメントを渡し、4観点の報告を1つに集約します（観点別の件数表＋全観点を通じた最終判定）。共通規律は `code-review-conventions`、各観点のチェックリストは各エージェントが持ちます。

### 4-2. 修正ループの制御

集約した結果に応じて、以下の条件でループを制御します（`code-review-loop` のループ制御に準拠）。

- **継続条件**: 致命的・高の指摘が1件以上ある場合は、コードを修正して再度並列レビューを依頼する。
- **正常終了**: 致命的・高の指摘がゼロになった時点でループを抜け、フェーズ5へ進む。
- **異常終了**: 3回修正してもなお致命的・高の指摘が残る場合はループを停止し、残存する指摘内容をユーザーに提示して人間による判断を求める。

中・低の指摘は、対応するか次フェーズ以降に持ち越すかをユーザーに確認してください。

---

## フェーズ5: ドキュメントの更新

実装の結果、設計ドキュメントと実際のコードの間に乖離が生じている箇所を特定し、ドキュメントを更新します。

### 5-1. 更新が必要な箇所の洗い出し

実装した内容を振り返り、以下の観点で各ドキュメントを確認してください。

**要件定義書 (`docs/specs/requirements-definition.md`)**
- 実装を通じて明確になった要件の補足・修正
- 実装段階で変更・追加された受け入れ条件

**基本設計書 (`docs/specs/basic-design.md`)**
- 実装により変更されたAPI仕様・画面仕様
- 追加・変更されたデータモデル・テーブル構成
- アーキテクチャや画面遷移の変更

**詳細設計書 (`docs/specs/detailed-design.md`)**
- 実装したクラス・メソッドの追加・変更
- 追加・変更されたシーケンス図
- インデックス・制約など物理設計の変更
- コード一覧・メッセージ一覧の追加

### 5-2. 更新箇所の提示とユーザー確認

更新が必要な箇所を一覧としてユーザーに提示し、更新して良いか確認してください。

更新不要と判断した場合（実装が設計通りで乖離がない場合）も、その旨を明示してください。

### 5-3. ドキュメントの更新

確認が取れたドキュメントを更新します。更新後は変更箇所のサマリーをユーザーに報告してください。設計ドキュメントを最新化してからフェーズ6へ進むことで、テスト仕様を正確な設計に基づいて作成できます。

---

## フェーズ6: テスト仕様作成・実施

更新済みの設計ドキュメントをもとに、テスト工程を実施します。テストは **V字モデル**に従い、各テストレベルを対応する設計ドキュメントに紐づけて構成します。**この対応関係（フェーズ）は不変**とし、**実行ツール（テストランナー・E2Eツールなど）はフェーズではなく、テストケースごとの実行手段（メタ属性）として扱います**（ツールが世代交代してもフェーズ構成は変えない）。具体的にどのツールを使うかは**プロジェクトの技術スタック（基本設計書）に従う**ものとし、本スキルは特定のツール名を固定しません。実際にツールを叩くのは、実行手段共通の差し戻しループ `test-loop`（生成役 `test-to-code`／実行役 `test-runner`）に委譲します。ツール固有の作法は実行手段ごとの conventions スキル（例: `pytest-conventions` / `playwright-conventions`）に閉じます。

| テストレベル | 対応する設計ドキュメント | 検証対象 | 体裁を読むスキル |
|---|---|---|---|
| 単体テスト | 詳細設計書 | クラス・関数の内部ロジック | `unit-testing` |
| 結合テスト | 基本設計書 | コンポーネント間の連携（バックエンド連携・画面↔コンポーネント連携の両方） | `integration-testing` |
| 総合（システム）テスト | 要件定義書 | 機能要件を利用者視点で満たすか | `system-testing` |

テスト仕様書の作成は、専任の **`testspec-writer` エージェント**に委譲します（フェーズ4で `code-review-loop` に委譲するのと同じ構造）。`testspec-writer` は渡されたテストレベルに応じて、対応する体裁スキル（`unit-testing` / `integration-testing` / `system-testing`）を読み、対応する設計書をインプットに仕様書を作成します。テストレベルと出力先の対応（V字モデル）は不変です。

本フェーズは **「仕様作成（6-1）」と「コード作成・実行（6-2）」を分離した2段構え**で進めます。**先に全テストレベルの仕様書を作り切り**、出揃った状態で確認してからコード生成・実行へ移ります。レベルごとに仕様とコードを往復しないでください（文脈が混ざってややこしくなるため）。

### 6-1. テスト仕様書の作成（全レベルまとめて）

この段階では**テストコードは作りません**。各レベルの仕様書をすべて作成・追記し、テスト網羅性を一括で確認できる状態にします。

仕様書の作成は、各レベルとも **`testspec-writer` エージェントを Agent ツールで起動**して行います。各 prompt に **テストレベル（unit / integration / system）** と、対象機能・参照すべき設計ドキュメントを渡します。`testspec-writer` はレベルに応じた体裁スキルを読み、対応する設計書をインプットに仕様書を該当パスへ作成・追記します。独立している3レベルは、1メッセージ内で同時に起動して並列に作成してかまいません。

- **単体テスト（必須）**: `testspec-writer` に `unit` を渡して起動し、`docs/tests/unit/<コンポーネント名>.md` に作成・追記します。実装した責務に対して必ず作成します。
- **結合テスト（連携があれば必須）**: コンポーネント間の連携を含む場合は `testspec-writer` に `integration` を渡して起動し、`docs/tests/integration/<フロー名>.md` に作成・追記します。
  - バックエンド連携（API↔DB↔外部↔バッチ）も、画面↔コンポーネント連携も、本レベルに含みます。
  - 各ケースの **`実行手段`**（`pytest` / `playwright` 等のツール名、または `manual`）をメタ属性として記録します。**結合テストは pytest と playwright が混在しうる**ので、ケース単位で明示します。
  - 単一コンポーネントで完結する場合は省略可とし、省略した理由を明示してください。
- **総合（システム）テスト（必須）**: `testspec-writer` に `system` を渡して起動し、`docs/tests/system/<フロー名>.md` に作成・追記します。要件定義書の機能要件を利用者視点で検証し、各ケースへ `要件ID` を紐づけて追跡可能にします。
  - 各ケースの **`実行手段`**（`playwright` 等のツール名、または `manual`）をメタ属性として記録します。総合テストはブラウザ操作が中心ですが、帳票・API応答の確認など別手段も混在しうるので、ケース単位で明示します。
  - 読み手に非エンジニア（QA/PM）を含むため、手順・期待結果は技術用語を使わず利用者視点で具体的に書きます。

仕様が出揃ったら、テスト網羅性をユーザーに提示して確認を得てから 6-2 へ進みます。

### 6-2. テストコードの作成・実行（仕様確定後）

出揃った仕様書のケースを、メタ属性 **`実行手段`** でグループ分けします（`manual` のケースは自動化対象外＝コード化しない）。テストレベルと実行手段は多対多なので、`(テストレベル, 実行手段)` の組ごとに分けます（例: 結合テストの pytest 群と playwright 群）。

各グループについて、付属の差し戻しループ `Skill('test-loop')` に、**テストレベル・実行手段・対象仕様書**（ブラウザ手段なら URL も）を渡して起動します。`test-loop` が生成役 `test-to-code` と実行役 `test-runner` を仲介し、「生成→実行→差し戻し（T）→再実行」を緑か人間確認待ちまで回します。実行手段が pytest でも playwright でもループ・エージェントは共通で、ツール差分は実行手段ごとの conventions スキルに閉じます。

- **コードで実行する手段（pytest 等）**: 速く決定的なので同期実行でよい。失敗診断はログ差分で行う（`pytest-conventions`）。
- **ブラウザ経由で実行する手段（playwright 等）**: 実行が重いため、本フェーズ内で同期実行せず、必要性をユーザーに提示したうえで別工程として起動してよい。失敗診断は実画面確認で行う（`playwright-conventions`）。

### 6-3. テストに関する原則

- **実行ツールはフェーズではなく実行手段**: 「E2E」はフェーズ名ではなく、ブラウザ経由で実行する手段の呼称として扱います。各テストケースには実行手段（プロジェクトの技術スタックで定義したツール、または `manual`）をメタ属性として記録し、ツールが変わってもテストレベルの構成は変更しません。
- **結果は仕様書に書き戻さない**: テスト結果（合否）はテスト仕様書に書き戻しません。仕様書は仕様の正本とし、実行結果は CI・テストレポート・エビデンス側で管理します。

### 6-4. 最終報告

すべての作業が完了したら、ユーザーに以下を報告してください。

- 実装した内容のサマリー
- 変更・作成したファイルの一覧（実装ファイル・ドキュメント・テスト仕様書）
- 実施したテストレベルと、省略したテストレベル（ある場合はその理由）
- 残課題（別工程に回した総合テスト/E2E など）
