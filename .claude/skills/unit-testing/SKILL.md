# 単体テスト仕様書作成スキル

このスキルは単体テスト仕様書を作成するためのスキルです。

## 前提条件

単体テスト仕様書を作成する前に以下のタスクが完了している必要があります。

- **詳細設計書が完成している**
  単体テストは詳細設計の各設計書をインプットとして作成されたプロダクトコードを検証するものです。詳細設計が完了していない場合は、先に詳細設計書を作成してください。承認済みの詳細設計書は `docs/specs/detailed-design.md` に保存されているはずです。

## 単体テスト仕様書の標準構成

以下の構成を基本とする。

1. テスト方針
2. テストデータ方針
3. テストケース一覧

## テストケースの記述形式

各テストケースは、見出し直下に固定フィールドのメタブロックを置き、その後に詳細セクションを続けるブロック形式で記述する（`./template.md` 参照）。

```markdown
## UT-LOGIN-001 ログイン成功

- **ID**: UT-LOGIN-001
- **観点**: 正常系
- **実行手段**: pytest
- **理由**: -

### 概要
...
### 前提条件
...
### 入力
...
### 期待結果
...
```

メタフィールドの規約は以下のとおり。

- **ID**: 見出しとフィールドの両方に持たせる。テストコード名・CIレポート・実行管理を貫通する共通キーとして使う（例: テスト名に `UT-LOGIN-001` を含める）。
- **観点**: 「テスト観点」で定義した観点名を記載する。
- **実行手段**: そのケースを実行する手段を1語で固定する（自由文禁止）。`pytest` などプロジェクトの技術スタックで定義したツール名、または自動化しない場合は `manual`。この値で実行手段ごとのグループ化・手動ケースの抽出を安定させる（`manual` を含めることで旧 `自動化` 項目を兼ねる）。
- **理由**: `実行手段: manual` の場合は必須とし、なぜ自動化できないかを1行で書く（例: 「視覚的なレイアウト確認のため」）。ツールを指定した場合は `-` でよい。理由を残すことで、後から手動ケースを棚卸しし、技術の進歩に応じて自動化を再評価できる。
- 合否などの実行結果はここに書かない。仕様書は仕様の正本であり、結果は CI / 実行管理側で持つ。

単体テストは原則コードで自動化する（既定の実行手段は技術スタックに従う。例: `pytest`）。入力と期待結果が明確なため、手順セクションは省略してよい（`parametrize` 等にそのまま対応する）。`manual` とする場合は理由を必ず添える。

## 単体テストの基本原則

以下の原則を踏まえてテスト仕様書を作成する。

**自動化を原則とする**

単体テストの実行は原則として自動化する。自動化が難しい場合（テスト対象の挙動が非決定論的など）は、自動化できない理由を明確にしたうえで手動実行方法を記載する。

**外部サービスに依存しない**

単体テストは外部サービスやシステムに依存しないように設計する。外部サービスの代わりにモックオブジェクト・スタブ・コンテナなどを使い、テスト対象コードの挙動だけを検証する。

**冪等性を確保する**

同じテストを何度実行しても同じ結果が得られること（冪等性）を確保する。これによりテストの再現性が保たれ、CI/CDのトリガーで複数回実行されても信頼できる結果を得られる。

**テスト容易性を意識した実装**

テスト計画と並行して、実装コードが以下の点を満たしているかレビューする。
- 単一責任原則（SRP）: クラス・関数は1つのことだけを行う
- 依存性の注入（DI）: モックを差し込みやすい構造にする
- グローバル状態・シングルトンの使用を避ける

## テスト観点

**テストケースを作成するとき、必ず以下の観点を確認し、該当するものをすべてカバーすること。** テンプレートの観点欄にはここで定義した観点名を記載する。

### 入力データ

| 観点 | 内容 |
| --- | --- |
| 正常値 | 期待される範囲内の正常なデータで適切に処理されるか |
| 境界値 | 最小値・最大値・その前後で正しく処理されるか |
| 異常値 | 不正な形式・範囲外のデータで適切にエラーになるか |
| 組み合わせ | 複数入力の組み合わせパターンを網羅的に確認する |
| NULL/None処理 | null・未定義値を許容する項目・許容しない項目それぞれで正しく処理されるか |
| 文字コード・特殊文字 | マルチバイト文字・絵文字・制御文字・HTMLタグを含む入力で正しく処理されるか |
| 日時・タイムゾーン | 日時の計算・比較・タイムゾーン変換が正しいか。月末・年末をまたぐ処理も確認する |

**異常値テストで確認すべき主なパターン:**
- 型チェック（期待する型以外の入力）
- 長さの制約（最小長未満・最大長超過）
- フォーマット検証（メールアドレス・電話番号・日付形式）
- 数値の範囲チェック
- 必須入力が空の場合
- 一意性制約の重複

### ロジック

| 観点 | 内容 |
| --- | --- |
| 繰り返し処理 | 0回・1回・通常回数・最大回数で正しく動作するか |
| 条件分岐 | すべての分岐（真・偽）が少なくとも1回実行されるか |
| 例外の発生 | 発生しうるすべての例外が適切な条件下で発生するか |
| 例外ハンドリング | 例外発生時にロールバック等の回復処理が正しく行われるか |
| 状態遷移 | オブジェクトが正しい順序で状態を遷移するか。不正な遷移がブロックされるか |
| 冪等性 | 同じ操作を複数回実行しても結果が変わらないか（PUT・DELETE等） |
| 非同期処理 | タイムアウト・キャンセル・エラー伝播が正しく処理されるか（非同期処理を使う場合のみ） |

### 出力データ

| 観点 | 内容 |
| --- | --- |
| 出力の正確性 | 出力データが仕様書の内容と一致しているか |
| エラー出力 | エラー発生時に適切なエラーメッセージが返るか |
| ログの正確性 | ログが正しいフォーマット・内容で出力されているか |
| ログレベル | エラー・警告・情報など適切なレベルでログが記録されているか |
| センシティブデータ | ログにパスワード・個人情報が含まれていない（マスクされている）か |

### セキュリティ

以下は代表的な観点の一覧である。セキュリティの観点はシステムの特性によって多岐にわたるため、プロジェクトの要件・使用技術・脅威モデルに応じて観点を追加すること。

| 観点 | 内容 |
| --- | --- |
| インジェクション防止 | ユーザー入力がSQLやLDAPクエリに直接組み込まれていないか |
| XSS防止 | ユーザー入力がHTMLやJavaScriptとして解釈されないようエスケープされているか |
| ディレクトリトラバーサル防止 | ファイルパスの入力が不正なファイルアクセスを引き起こさないか |
| 認証・アクセス制御 | 機能に対して正常に認証・認可が機能しているか |

## テストデータの方針

- 単体テストに個人情報（氏名・住所・電話番号）や本番環境の顧客情報を使用しない
- 本番データを元にしたテストデータを使う場合は、事前にマスキングを確認する
- テストデータの生成・管理・廃棄のプロセスを明確にし、適切なアクセス制御を行う
- テスト環境と本番環境を明確に分離し、テストデータが本番に漏れないようにする

## 単体テスト仕様書作成プロセス

### 1. 関連ドキュメントの確認

まず、承認済みの要件定義書、基本設計書、詳細設計書を確認し、単体テストで保証すべき責務と、結合テスト以降へ委ねる範囲を整理する。

```bash
Read('docs/specs/requirements-definition.md')
Read('docs/specs/basic-design.md')
Read('docs/specs/detailed-design.md')
```

### 2. テスト対象と責務境界の整理

以下を一覧化する。

- 対象クラス、関数、モジュール
- 各対象が担う責務
- モック、スタブ、フェイクに置き換える依存先
- 単体テストで確認する事項と、結合テストへ委ねる事項

結合点そのものではなく、各コンポーネント内部の判断、変換、検証、例外処理を確認対象として整理する。

### 3. 単体テスト仕様書ドラフトの生成

テンプレート（`./template.md` がある場合はそれに従う）に沿って、単体テスト仕様書を生成する。

**保存先**: `docs/tests/unit/<コンポーネント名>.md`（例: `docs/tests/unit/user.md`）

- コンポーネント名はテスト対象のクラス・モジュール名に対応したケバブケースとする
- **ファイルが既に存在する場合**: ファイルの末尾に新しい機能のセクションを追記する。既存の内容は変更しない
- **ファイルが存在しない場合**: 新規作成する

機能追加でテストを追記する際のセクション形式:

```markdown
## <機能名>（YYYY-MM-DD 追加）

### テストケース一覧
...
```

### 4. 単体テスト仕様書のレビューと改善

生成された単体テスト仕様書を以下の観点でレビューする。

- 詳細設計で定義された責務が、対象クラスや関数ごとにテスト対象へ落とし込まれているか
- 正常値、境界値、異常値、例外処理、状態遷移などの主要観点が漏れていないか
- 外部依存をモックやスタブで置き換える前提が明記され、単体テストとして独立実行できるか
- 期待結果が戻り値、状態変化、例外、ログ出力など観測可能な形で書かれているか
- テストデータの初期化方法と再実行性が定義され、順序依存のない構成になっているか
- 結合テストで確認すべき連携観点が、単体テストへ過剰に混入していないか

レビューで不足や曖昧さが見つかった場合は、以下の順で改善する。

1. テスト対象の責務漏れを補完する
2. 期待結果を観測可能な表現に書き換える
3. モック、スタブ、テストデータの前提を追記する
4. 結合テスト寄りのケースを削減し、単体観点に寄せる

特に、次のような記述はそのまま残さない。

- 「正しく動作することを確認する」だけで、何をもって合格とするか不明な記述
- モック化対象や前提状態が未記載のテストケース
- 境界値や異常値がなく、正常系だけで構成された計画
- 複数コンポーネントの連携確認が中心で、単体責務の確認になっていないケース

レビュー完了時には、少なくとも次の状態になっていること。

- 単体テスト仕様書だけを読んで、各対象の責務と確認観点を説明できる
- 正常系、異常系、境界値、例外系の主要ケースが識別できる
- 実装者が、そのままテストコード作成に着手できる粒度になっている

必要に応じて、レビュー結果として以下も合わせて残す。

- 単体テスト対象外とした責務と理由
- モック、スタブ化した依存先とその理由
- 結合テストまたは総合テストへ持ち越す論点

### 5. ユーザー承認の取得

単体テスト仕様書が完了したら、次の工程に進む前に、必ず承認を得てください。

### 6. 単体テスト仕様書の保存

ユーザーの承認を得て完成となった単体テスト仕様書を保存してください。

- 既存ファイルへの追記の場合: 該当ファイルの末尾にセクションを追記する
- 新規ファイルの場合: `docs/tests/unit/<コンポーネント名>.md` として保存する
