# テスト 差し戻しループの進め方（実行手段共通）

承認済みテスト仕様書（`docs/tests/unit/*` / `docs/tests/integration/*` / `docs/tests/system/*`）と**実行手段**を起点に、テストを緑にするまで回す**工程の正本**。
**実行手段（pytest / playwright …）が変わっても、ループ・生成役・実行役は変えない**。変わるのは渡す引数（実行手段）と、その手段に対応する実装プロファイル（conventions）スキルだけ。
本スキルは「**誰がいつ何を起動し、結果をどう振り分けるか**」だけを定義する。ツール固有の作法（配置・診断方法・証跡先）は規約スキルが持つ。
テスト結果は仕様書に書き戻さない（結果の正本は各規約に定義されたレポート/証跡）。

## 前提：責務分離（崩さない）
- **生成役 = test-to-code** … テストコードを書く／差し戻し修正する。実行はしない。渡された実行手段に対応する conventions スキルを自分で見分けて読み、書き方を決める。
- **実行役 = test-runner** … 実行して結果を T/I/E に切り分け報告する。コードは編集しない（Edit を持たない）。渡された実行手段に対応する conventions スキルを自分で見分けて読み、診断方法・証跡先を決める。
- **メイン（あなた＝オーケストレータ）** … 両者を `Agent` ツールで起動し、報告を読んで次の一手を決める。サブエージェントは互いを直接呼べない。

> なぜ実行役にコード編集をさせないか：「緑にするために期待値（assert/expect）を実挙動へ書き換える」のが本物のバグを隠す最悪パターンだから。生成と実行を分けるのがその防波堤。実行手段が何であってもこの分離は崩さない。

## 入力（起動時に決める）
1. **テストレベル**: `unit` / `integration` / `system`（V字モデル。不変）。
2. **実行手段**: `pytest` / `playwright` など（基本設計書の技術スタックで定義。可変＝メタ属性）。その実行手段を description に明記した実装プロファイル（conventions）スキルが配備されている前提（生成役・実行役が description で見分けて読む）。
3. **対象仕様書**: 承認済みの `docs/tests/{unit|integration|system}/{...}.md`。未承認なら、まず人間のレビュー・承認を待つ。
4. **対象URL**（ブラウザ実行手段のときのみ）: 例 `https://www.saucedemo.com/`。

> **1起動 = 1実行手段**。テストレベルと実行手段は多対多（例: 結合テストに pytest と playwright が混在）。1つの仕様書に複数の実行手段が混在する場合は、**呼び出し側（feature フェーズ6-2 等）が仕様書のケースを実行手段でグループ分けし、実行手段ごとに本ループを起動する**。各起動では、その実行手段に一致するケースだけを対象にする。

## 起動の流れ
1. **入力を確認** … 上記を確定する。仕様書が未承認なら停止して承認を待つ。
2. **環境を確認** … 実行手段（ツール・依存・ブラウザ操作環境など）が使えるか確認。未導入なら導入してから進む（実行役は環境を直さない）。
3. **生成** … `Agent(subagent_type: "test-to-code")` を起動。prompt に「テストレベル」「**実行手段**」「対象仕様書パス」（ブラウザ手段なら「URL」）「**実行手段が一致するケースを漏らさず実装**（他手段・`manual` は対象外）」を渡す。生成役は渡された実行手段に対応する conventions スキルを自分で見分けて読む。
4. **実行** … `Agent(subagent_type: "test-runner")` を起動。prompt に「テストレベル」「**実行手段**」「対象テスト」（ブラウザ手段なら「URL」）を渡す。報告（サマリ＋失敗ケースの T/I/E 分類＋差し戻し先）を受け取る。
5. **振り分け**（下記ルール）。
6. 緑、または人間確認待ちになるまで 3〜5 を繰り返す。

結果の正本は各規約に定義されたレポート/証跡。仕様書には書き戻さない（仕様書は設計の入力）。

## 差し戻しの振り分け
report の「差し戻し先」列に従い、メインが次の起動先を決める：

| 分類 | 意味 | 次の一手 |
|---|---|---|
| T | テスト側の不備（症状は実行手段ごと） | test-to-code に差し戻して修正 → 再実行 |
| I | 実装バグ疑い（仕様と実挙動が食い違う） | **人間へ報告して停止**（コードで吸収しない） |
| E | 環境・依存・データ起因 | **人間へ報告して停止** |

差し戻し修正は `Agent(subagent_type: "test-to-code")` を再起動し、report の T 行（ケースID・原因・修正提案）と実行手段をそのまま prompt に渡す。

## 上限・停止条件
- **T の差し戻しは最大3周**。3周しても落ちるなら I を疑い、人間へ上げて停止する。
- I・E が1件でも出たら、その時点で人間へ報告して停止する（自動ループを続けない）。
- **期待結果(assert/expect)を通すために緩めない**。緑にするための改変は I の隠蔽になる。

## 実行コスト上の注意
- ブラウザ経由の実行手段（playwright 等）は実行が重い。本フェーズ内で同期実行せず、必要性をユーザーに提示したうえで別工程として起動してよい。コード実行手段（pytest 等）は速く決定的なので同期実行でよい。

## 各ターンで人間に返すもの
- 全体 pass/fail サマリ、テストレベル、実行手段、今が何周目か、差し戻し先の内訳
- レポート/証跡の場所（対応する conventions スキルに定義）
- I/E があれば、停止理由と人間に判断してほしい点を明示
