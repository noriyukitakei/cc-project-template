# 総合（システム）テスト仕様書

各テストケースは「メタブロック（固定フィールド）＋詳細セクション」のブロック形式で記述する（単体・結合テスト仕様書と同一の体裁）。

- メタフィールドは値を固定し、後段の自動抽出（実行手段ごとのグループ化・手動ケースの抽出など）を安定させる。
  - `実行手段` は `playwright` 等のツール名、または `manual` のいずれか（自由文禁止）。`manual` が旧 `自動化: manual` を兼ねる。
  - 総合テストはブラウザ操作が中心になりがちだが、API応答・帳票出力の確認など別手段も混在しうるので、ケースごとに明示する。
  - `実行手段: manual` の場合は `理由` を必須とする（なぜ自動化できないかを1行で）。
- `ID` は見出しとフィールドの両方に持たせ、テストコード・CIレポート・実行管理を貫通するキーとする（接頭辞は `ST-`）。
- `要件ID` は必須。要件定義書のどの機能要件を検証するかを紐づけ、要件→ケースの追跡を可能にする。
- 合否などの実行結果はここに書かない（仕様書は仕様の正本であり、結果は CI / 実行管理側で持つ）。
- 読み手に非エンジニア（QA/PM）を含む。セレクタ・コード・内部用語は書かず、手順は人間の操作、期待結果は利用者が観測できる事象で書く。

## ST-LOGIN-001 正しい情報でログインしダッシュボードを見る

- **ID**: ST-LOGIN-001
- **観点**: 正常系シナリオ
- **実行手段**: playwright
- **理由**: -
- **要件ID**: REQ-12

### 概要

登録済みの利用者が、正しいメールアドレスとパスワードでログインし、自分のダッシュボードを閲覧できることを確認する。

### 前提条件

- 利用者「test@example.com」が登録済みであること
- 未ログイン状態であること

### 手順

1. ログイン画面を開く
2. メールアドレスとパスワードを入力する
3. 「ログイン」ボタンを押す

### 期待結果

- ダッシュボード画面に切り替わる
- 画面右上に利用者の氏名が表示される
- 「ようこそ」のメッセージが表示される

### 備考

主要ブラウザ（Chrome / Safari）で確認する。

## ST-LOGIN-002 パスワードを間違えたときのエラー案内

- **ID**: ST-LOGIN-002
- **観点**: 入力エラー提示
- **実行手段**: playwright
- **理由**: -
- **要件ID**: REQ-12

### 概要

利用者がパスワードを誤って入力した場合に、分かりやすいエラーメッセージが表示され、再入力できることを確認する。

### 前提条件

- 利用者「test@example.com」が登録済みであること
- 未ログイン状態であること

### 手順

1. ログイン画面を開く
2. メールアドレスを正しく、パスワードを誤って入力する
3. 「ログイン」ボタンを押す

### 期待結果

- ログイン画面のまま、ダッシュボードには切り替わらない
- 入力欄の近くに「メールアドレスまたはパスワードが正しくありません」と表示される
- パスワード欄が空になり、再入力できる状態になる

### 備考

エラーメッセージに、どちらが間違っているか（メール／パスワード）を特定できる文言は出さない（要件のセキュリティ方針による）。

## ST-REPORT-001 月次売上レポートのPDF出力

- **ID**: ST-REPORT-001
- **観点**: 通知・帳票
- **実行手段**: manual
- **理由**: 出力されたPDFの体裁（レイアウト崩れ・文字化け）の妥当性は人の目視判断が要るため

### 概要

管理者が月次売上レポートをPDFで出力し、内容が要件どおりであることを確認する。

### 前提条件

- 管理者権限でログイン済みであること
- 対象月に売上データが登録済みであること

### 手順

1. レポート画面を開く
2. 対象月を選択する
3. 「PDF出力」ボタンを押す
4. ダウンロードされたPDFを開く

### 期待結果

- PDFがダウンロードされる
- PDFの表紙に対象月と会社名が表示される
- 売上合計が画面表示の金額と一致する
- レイアウト崩れ・文字化けがない

### 備考

帳票の自動化はレイアウト検証の精度の都合で見送る。数値の一致のみ別途 playwright で検証するケースを設けてもよい。
