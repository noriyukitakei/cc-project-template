# 総合（システム）テスト仕様書作成スキル

このスキルは総合（システム）テスト仕様書を作成するためのスキルです。

総合テストは V字モデルで **要件定義書に対応**するテストレベルであり、「実装が要件定義で約束した機能要件を、利用者視点で満たしているか」を検証します。単体テスト（詳細設計に対応・内部ロジック）や結合テスト（基本設計に対応・コンポーネント間連携）とは検証の高さが違うため、内部実装ではなく**利用者が観測できる振る舞い**で合否を語るのがこのレベルの肝です。

## 前提条件

総合テスト仕様書を作成する前に以下が完了している必要があります。

- **要件定義書が完成している**
  総合テストは要件定義書をインプットとして、機能要件が満たされているかを検証するものです。検証の正本がない状態では網羅性を担保できません。承認済みの要件定義書は `docs/specs/requirements-definition.md` に保存されているはずです。要件が確定していない場合は、先に要件定義書を作成してください。
- **基本設計書・詳細設計書も参照できる**
  利用者視点のシナリオを具体的な操作手順に落とすには、画面遷移や機能の振る舞い（基本設計）を参照する必要があります。検証の主軸はあくまで要件ですが、手順を書くために設計書も読みます。

## 総合テスト仕様書の標準構成

以下の構成を基本とする。

1. テスト方針
2. テスト対象範囲（検証する機能要件の一覧と、要件IDとの対応）
3. テスト環境方針
4. テストデータ方針
5. テストケース一覧

## テストケースの記述形式

各テストケースは、見出し直下に固定フィールドのメタブロックを置き、その後に詳細セクションを続けるブロック形式で記述する（`./template.md` 参照）。**形式は単体・結合テスト仕様書と同じブロック形式に揃える**。

```markdown
## ST-LOGIN-001 正しい情報でログインしダッシュボードを見る

- **ID**: ST-LOGIN-001
- **観点**: 正常系シナリオ
- **実行手段**: playwright
- **理由**: -
- **要件ID**: REQ-12

### 概要
...
### 前提条件
...
### 手順
...
### 期待結果
...
```

メタフィールドの規約は以下のとおり。

- **ID**: 見出しとフィールドの両方に持たせる。テストコード名・CIレポート・実行管理を貫通する共通キーとして使う（例: テスト名に `ST-LOGIN-001` を含める）。接頭辞は総合テストを表す `ST-` を用いる。
- **観点**: 「テスト観点」で定義した観点名を記載する。
- **実行手段**: そのケースを実行する手段を1語で固定する（自由文禁止）。`playwright`（画面操作をブラウザで）などプロジェクトの技術スタックで定義したツール名、または自動化しない場合は `manual`。**総合テストはブラウザ操作が中心になりがちだが、API応答や帳票出力の確認など別手段も混在しうる**ため、ケースごとにこの値で実行手段を明示する（`manual` を含めることで旧 `自動化` 項目を兼ねる）。後段はこの値で実行手段ごとにグループ化して `test-loop` を起動する。
- **理由**: `実行手段: manual` の場合は必須とし、なぜ自動化できないかを1行で書く（例: 「帳票の見た目の妥当性は人の目視判断が要るため」）。ツールを指定した場合は `-` でよい。理由を残すことで、後から手動ケースを棚卸しし、技術の進歩に応じて自動化を再評価できる。
- **要件ID**: そのケースが検証する機能要件（要件定義書の項番）を記載する。**総合テストは要件定義に対応するため、追跡用に必ず記載する**。1ケースが複数要件にまたがる場合はカンマ区切りで列挙してよいが、できれば1ケース1要件に分けると網羅性を確認しやすい。
- 合否などの実行結果はここに書かない。仕様書は仕様の正本であり、結果は CI / 実行管理側で持つ。

総合テストは、利用者の一連の操作（段取り）と画面の反応が入力から導出できないため、自動化する全ケースで **手順** を必須とする（手順がテストコード生成の入力になる）。手順は「人間の操作と観測ポイント」の粒度で書き、セレクタや内部APIのURL、assert する具体値などの実装詳細はテストコード側に委ねる。

## 総合テストの基本原則

以下の原則を踏まえてテスト仕様書を作成する。

**利用者視点で合否を語る**

総合テストは「実装がどう動いたか」ではなく「利用者が約束された価値を得られたか」を確認するレベルである。期待結果は内部状態やレスポンスボディの構造ではなく、利用者が画面・帳票・通知で**観測できる事象**で書く（例: 「注文完了画面に注文番号が表示される」「確認メールが届く」）。DB状態やログは、利用者視点の結果を補強する根拠としてのみ補足する。

**要件への追跡可能性を担保する**

各ケースは要件定義書のどの機能要件を検証するのかを `要件ID` で明示する。逆に、要件定義書の機能要件が少なくとも1つ以上のケースでカバーされているかを必ず突き合わせる。要件→ケースの対応表を作ると抜けを発見しやすい。受け入れ判断の根拠になるため、ここが総合テストの中心になる。

**業務シナリオ単位で通しで確認する**

単体・結合が部品や接続点を見るのに対し、総合テストは利用者の業務フローを開始から完了まで通しで確認する。複数画面・複数機能をまたいで、利用者の目的が達成できるか（例: 「会員登録 → ログイン → 商品購入 → 履歴確認」）をシナリオとして検証する。

**非エンジニアがレビューできる言葉で書く**

総合テスト仕様書の読み手には QA・PM・業務担当など非エンジニアを含む。セレクタ・コード・内部用語は書かない。手順は人間の動作（「〜画面を開く」「〜を入力する」「〜ボタンを押す」）として、期待結果は「画面に何が起きるか」を具体的に書く。「正しく表示される」のような曖昧語は使わない。

**異常系・例外シナリオも利用者視点で確認する**

正常系の完走だけでなく、利用者が誤操作したとき・入力を間違えたとき・処理が失敗したときに、分かりやすいエラーメッセージや回復導線が提示されるかを確認する。利用者が次に何をすればよいか分かる状態になっているかが合否基準になる。

## テスト観点

**テストケースを作成するとき、必ず以下の観点を確認し、該当するものをすべてカバーすること。** テンプレートの観点欄にはここで定義した観点名を記載する。観点は「機能要件を利用者視点で満たすか」を軸に構成している。

### 機能要件の充足

| 観点 | 内容 |
| --- | --- |
| 正常系シナリオ | 利用者の主要な業務目的が、開始から完了まで一連の操作で達成できるか |
| 代替フロー | 同じ目的を別経路（別画面・別手順）で達成する場合も成立するか |
| 要件網羅 | 要件定義書に列挙された機能要件が、少なくとも1ケースで検証されているか |
| 受け入れ基準 | 要件に受け入れ基準が定義されている場合、その基準を満たすことを確認できるか |
| 業務ルール | 割引計算・上限判定・必須業務項目など、要件で定めた業務ルールが利用者から見て正しく適用されるか |

### 利用者視点の異常系・例外

| 観点 | 内容 |
| --- | --- |
| 入力エラー提示 | 利用者が誤った入力をしたとき、分かりやすいエラーメッセージが該当箇所に表示されるか |
| 操作の中断・取消 | 処理の途中で取消・戻る操作をしても、利用者の意図どおりに中断・復帰できるか |
| 失敗時の回復導線 | 処理が失敗したとき、利用者が次に取るべき行動（再試行・問い合わせ等）が案内されるか |
| 境界・大量データ | 0件・1件・大量件数など、利用者が遭遇しうる端のケースで表示や操作が破綻しないか |

### 権限・状態による振る舞い

| 観点 | 内容 |
| --- | --- |
| 権限別の利用可否 | 利用者の役割（一般・管理者・未ログイン等）に応じて、見える機能・操作できる機能が要件どおりか |
| 状態遷移の整合 | 申請中・承認済み・キャンセル等、業務ステータスに応じて利用者ができる操作が正しく変わるか |
| 機能横断の整合 | ある画面での操作が、別画面・別機能に正しく反映されるか（登録後の一覧反映、更新後の再表示など） |

### 利用者体験・運用

| 観点 | 内容 |
| --- | --- |
| 表示の正確さ | 金額・日時・件数・氏名などの表示が、利用者の期待どおり（書式・タイムゾーン含む）に出るか |
| 通知・帳票 | メール・通知・PDF帳票など、利用者に届く成果物が要件どおりの内容で生成されるか |
| 多言語・文字種 | 要件で対応する言語・文字種（マルチバイト・特殊文字）で表示や入力が破綻しないか |
| アクセシビリティ・操作性 | 要件で定めた操作性（キーボード操作・主要ブラウザ対応等）の前提を満たすか |
| 体感性能 | 主要シナリオ実行時に、利用者が待たされすぎず操作を完了できるか（明らかな劣化・タイムアウトがないか） |

> セキュリティや性能の網羅的な検証は専用のテスト（性能テスト・脆弱性診断等）に委ね、総合テストでは「要件で利用者に約束した範囲」を利用者視点で確認することに集中する。プロジェクトの要件に応じて観点を追加すること。

## テストデータと環境の方針

- 総合テストに個人情報や本番環境の顧客情報を使用しない。本番データを元にする場合は事前にマスキングを確認する
- 本番に近い構成（画面・主要な外部連携を含む通し環境）で実施することを基本とし、スタブで代替する範囲があれば理由とともに明示する
- シナリオごとに、初期状態（登録済みデータ・ログイン状態など）、実行手順、期待される最終状態を定義する
- 通知・メール・帳票を伴うケースは、それらの確認方法（受信箱・出力先）を手順に含める
- 共有環境を使う場合は、データの命名規則・利用者アカウントの使い分け・後始末の手順を明示し、テスト順依存を避ける

## 総合テスト仕様書作成プロセス

### 1. 関連ドキュメントの確認

まず、承認済みの要件定義書を中心に、基本設計書・詳細設計書を確認し、どの機能要件を利用者視点で検証するかを整理する。

```bash
Read('docs/specs/requirements-definition.md')
Read('docs/specs/basic-design.md')
Read('docs/specs/detailed-design.md')
```

### 2. 検証対象の機能要件とシナリオの整理

以下を一覧化する。

- 検証対象の機能要件（要件ID付き）
- 各要件を達成する利用者シナリオ（業務フロー）
- 利用者の役割（権限）ごとに分けるべきシナリオ
- 正常系・代替フロー・異常系・例外の優先度

要件→シナリオ→ケースの対応を意識し、要件の取りこぼしがないかを確認する。単体・結合で担保済みの内部観点は繰り返さず、利用者視点の結果に寄せる。

### 3. 総合テスト仕様書ドラフトの生成

テンプレート（`./template.md` がある場合はそれに従う）に沿って、総合テスト仕様書を生成する。

**保存先**: `docs/tests/system/<フロー名>.md`（例: `docs/tests/system/member-purchase-flow.md`）

- フロー名はテスト対象の利用者シナリオ・業務フローを表すケバブケースとする
- **ファイルが既に存在する場合**: ファイルの末尾に新しい機能のセクションを追記する。既存の内容は変更しない
- **ファイルが存在しない場合**: 新規作成する

機能追加でテストを追記する際のセクション形式:

```markdown
## <機能名>（YYYY-MM-DD 追加）

### テストケース一覧
...
```

### 4. 総合テスト仕様書のレビューと改善

生成された総合テスト仕様書を以下の観点でレビューする。

- 要件定義書の機能要件が、少なくとも1つ以上のケースで検証対象になっているか（要件→ケースの対応に抜けがないか）
- 各ケースに `要件ID` が紐づき、何を根拠に合格とするかが要件までたどれるか
- 期待結果が、利用者が画面・帳票・通知で観測できる事象として書かれているか（内部状態の説明に偏っていないか）
- 正常系だけでなく、入力エラー・操作取消・失敗時の回復導線など利用者視点の異常系が含まれているか
- 権限別・状態別の振る舞いの違いが、必要なシナリオで検証されているか
- 手順が人間の操作として書かれ、非エンジニアがレビューできる言葉になっているか
- テストデータの初期状態・最終状態・後始末が定義され、再実行可能になっているか

レビューで不足や曖昧さが見つかった場合は、以下の順で改善する。

1. 要件→ケースの対応の漏れを補完する
2. 期待結果を利用者が観測できる表現に書き換える
3. 異常系・権限別シナリオを追記する
4. 単体・結合と重複する内部観点を削減し、利用者視点に寄せる

特に、次のような記述はそのまま残さない。

- 「正しく表示される」「問題なく動作する」だけで、利用者が何を見て合格と判断するか不明な記述
- 要件IDが紐づかず、どの要件を検証しているのか追跡できないケース
- 正常系の完走のみで、誤操作・失敗時に利用者がどうなるかを確認しない計画
- セレクタや内部API・コードが書かれ、非エンジニアがレビューできないケース

レビュー完了時には、少なくとも次の状態になっていること。

- 総合テスト仕様書だけを読んで、どの要件を利用者視点でどう確認するか説明できる
- 要件定義書の機能要件とケースの対応が追跡できる
- QA・PM を含む読み手が、そのままテスト実施または自動化に着手できる粒度になっている

必要に応じて、レビュー結果として以下も合わせて残す。

- 単体・結合で担保済みとして総合テスト対象外にした観点
- 実環境での再現が難しくスタブ・手動で代替する範囲と理由
- 性能テスト・脆弱性診断など別工程へ委ねる論点

### 5. ユーザー承認の取得

総合テスト仕様書が完了したら、次の工程に進む前に、必ず承認を得てください。

### 6. 総合テスト仕様書の保存

ユーザーの承認を得て完成となった総合テスト仕様書を保存してください。

- 既存ファイルへの追記の場合: 該当ファイルの末尾にセクションを追記する
- 新規ファイルの場合: `docs/tests/system/<フロー名>.md` として保存する
